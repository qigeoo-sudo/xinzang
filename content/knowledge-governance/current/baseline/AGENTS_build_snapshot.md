- 导师原始素材：`D:\database\mentors\<导师>\` 下的 audio、word 等来源目录。
- 导师加工资产：`D:\database\mentors\<导师>\work\<版本>\`。
- 
- 当前内容生产规范快照：`D:\database\knowledge-governance\current\`。导师目录中的旧JSONL保留为来源与历史证据。Trae主代码仓库另有应用集成快照；每次交接前必须按下方“双快照对账”规则核对，不能假设两处天然同步。
- 当前导师 Prompt：`D:\database\knowledge-governance\current\prompts\`。组装时先加载全局 System Policy，再加载对应导师 Prompt。
- `D:\database\mentors\aaaa bbb\` 是用户复制的空结构目录，始终忽略，不视为导师或待加工素材。
- `D:\database\mentors\z-others\` 是历史交付与旧代码归档，默认只读，不作为当前版本来源。
- `D:\database\xinzang\` 是旧网站代码副本，默认只读，不在此组装或发布导师内容。
- 不再读取或修改 `D:\xinzang`、`D:\xinzang git traecode` 中的导师 Prompt 和知识卡。

1. 当前流程默认以下前置动作已经由人工或既有运营流程完成：飞书妙记操作指南和第一轮访谈大纲已经发送给导师。

### 4A. Codex调用访谈材料时的合并稿优先规则

1. 本规则同时适用于Codex处理第一轮和第二轮访谈资料。Codex接到构建、更新、审核或补全导师Prompt和知识卡的命令后，在调用某轮音频和文字稿之前，必须先检查该轮对应的 `audio`、`word` 及来源目录中的文件名。
2. 文件名匹配不区分大小写。若音频文件名包含 `full interview`，将其视为该轮所有零散音频按原始顺序合并后的完整访谈音频，并优先把它作为该轮唯一的音频分析输入。
3. 若文字稿文件名包含 `full transcript`，将其视为该轮所有零散文字稿合并后的完整访谈文字稿，并优先把它作为该轮唯一的文字处理输入。
4. `full interview` 与 `full transcript` 独立判断：只存在其中一种时，该类型使用合并稿，另一类型仍按现有零散文件规则处理。
5. 存在已确认合并稿时，不需要把同一轮的全部零散音频或文字稿再次逐份提交给Codex或模型处理，避免重复分析、重复计数和上下文浪费。零散原件仍须原样保留，不得移动、改名、覆盖或删除。
6. Codex必须在source manifest和审计中说明所选合并稿、原始零散文件数量、选择依据、文件大小和SHA-256。若已有合并记录、清单或时长信息，应核验合并稿覆盖全部零散文件且顺序正确；核验通过后不再重复分析零散文件。
7. 若合并稿大小、时长、结尾、章节或清单显示可能缺段、顺序错误或与零散原件冲突，必须停止“合并稿唯一输入”假设，报告问题并回查相关零散文件，不得因为文件名含 `full interview` 或 `full transcript` 就忽略明显缺失。
8. 若同一轮出现多个包含 `full interview` 或多个包含 `full transcript` 的候选文件，优先使用source manifest明确指向或已验证为最新完整版本的文件。无法唯一确定时进入 `waiting_human_input`，不得按修改时间盲选。
9. 若不存在上述合并稿，才按既有规则调用全部相关零散音频和文字稿，并在必要时生成规范化合并稿。人工文字稿仍是事实主来源，完整音频仍用于完整性、术语和语言风格复核；合并稿优先规则不改变来源权威顺序。

## 知识卡四分类

每张知识卡必须且只能属于以下一类：

1. `internal_pending`（内部待审）：确属知识、但只供内部使用且尚未通过审核；仅开发、审核与测试环境可用；不得进入生产推理。
2. `internal_approved`（内部通过）：确属知识、只供内部使用且已通过审核；可供生产端内部计算或判断，但永远不得向用户披露。
3. `external_pending`（外部待审）：内容拟面向用户，但尚未通过审核；仅测试环境和明确授权的内测用户可用；不得进入普通生产流量。
4. `external_approved`（外部通过）：已通过面向用户的内容审核，可自然融入普通生产回答。

分类原则：

- `knowledgeClass` 必须且只能取以上四个枚举值，不再另设审核状态字段。
- `disclosureMode` 必须且只能取 `none`、`generalized`、`exact`。内部类必须为 `none`；外部类按允许的披露精度选择 `generalized` 或 `exact`。
- “已部署”“已进入生产数据库”“已启用”不是第五种分类；如需记录，只使用独立的部署字段。
- 内部类只用于真正需要以“知识”形式保存的内部事实。系统安全规则、回答策略、必要追问、路由、人格表达、授权、版本管理、访谈计划、置信度与发布流程不属于知识卡。
- 导师履历、行业观点、职业建议和可自然融入用户回答的案例归外部类；通过审核后是“外部通过”，未通过时是“外部待审”。
- “外部”不表示向用户展示原始知识卡对象。无论分类如何，卡号、字段名、状态、来源定位和检索过程都不得上屏。

## 不得制作成知识卡的内容

- 全体导师共同遵守的安全、隐私、危机处理与防泄露规则：进入全局 System Prompt。
- 某位导师的语气、追问方式、推理顺序、回答边界与人工升级偏好：进入该导师 Prompt 或能力/路由配置。
- 访谈轮次合并、内容有效期、冲突处理：进入版本清单或变更日志。
- 录音、文字稿、形象、语音克隆和公开范围的授权：进入授权与审计档案。
- 下一轮要追问的主题：进入访谈待办。
- 证据来源、置信度、审核过程：进入卡片元数据或审计记录，不单独占用知识卡编号。
- 知识卡标题默认不重复导师姓名；卡号和 `mentorId` 已经完成归属标识。

## 知识卡当前结构

当前结构版本为 `1.1`，规范文件位于 `D:\database\knowledge-governance\knowledge_card.schema.json`。每张卡使用以下字段：

```json
{
  "schemaVersion": "1.1",
  "cardId": "TIN-R1-001",
  "mentorId": "tina",
  "domain": "领域",
  "title": "标题不重复导师姓名",
  "caseText": null,
  "coreView": "核心观点",
  "reasoning": "观点理由；案例卡中用于保存导师评点",
  "applicableTo": "适用场景",
  "notApplicableTo": "不适用场景",
  "prerequisites": "使用前提",
  "exceptions": "例外",
  "risks": "隐私、误用和过度泛化风险",
  "source": ["来源定位"],
  "confidence": "high",
  "knowledgeClass": "external_approved",
  "disclosureMode": "generalized",
  "validFrom": "2026-09",
  "reviewAfter": "2027-09",
  "version": "v0.1"
}
```

案例卡规则：

- `caseText` 是可空字段。普通观点卡使用 `null`；案例卡保存案例本身，包括必要背景、经过和结果。
- `reasoning` 在案例卡中保存导师对案例的评点、判断理由和建议，不新增 `mentorCommentary`。
- `coreView` 只保留从案例提炼的一句话核心判断，不重复案例全文或完整评点。
- 默认一个独立案例一张卡。字数不是拆卡依据；100至400字案例以及相应评点可以完整保存。只有包含多个可独立检索的案例、矛盾或结论时才拆卡。
- 目前不强制增加 `cardType`；系统以 `caseText` 是否为空识别案例卡。如未来出现多种复杂内容类型，再升级结构版本。
- 真实人物、公司、项目、金额、时间组合等可能造成重新识别时，优先去标识化并使用 `disclosureMode=generalized`；只有明确允许精确披露时才使用 `exact`。
- `caseText` 与 `reasoning` 共用同一 `knowledgeClass` 和 `disclosureMode`，不得只批准评点却泄露未批准的案例细节。
